Ниже представлены спецификации для каждого требования, оформленные по заданной структуре. Спецификации составлены таким образом, чтобы агент Gigacode мог однозначно интерпретировать задачу и реализовать решение.

## Спецификация 1: Общедоступный домен (бесплатно)

### Намерение
Обеспечить доступ к развернутым сервисам (дашборд, система логирования, приложение, ArgoCD) через единое общедоступное доменное имя без дополнительных финансовых затрат.

### Требования
1. Зарегистрировать бесплатный общедоступный домен (субдомен) у одного из провайдеров, предоставляющих такую возможность.
2. Домен должен быть доступен из публичной сети Интернет.
3. Домен должен поддерживать настройку DNS-записей (A, CNAME) для указания на внешний IP-адрес или балансировщик нагрузки в Cloud.ru.

### Ограничения
1. **Бесплатность** — использование платных доменов не допускается.
2. **Стабильность** — предпочтение отдается сервисам с documented политикой продления (например, DNSHE с 180-дневным окном продления).
3. **Регистрация** — некоторые сервисы требуют подтверждения использования или прохождения верификации.
4. Домен должен быть делегирован на DNS-серверы, управляемые проектом (возможно использование NS-делегирования).

### Контекст
- Домен будет использоваться как единая точка входа для всех публичных сервисов проекта.
- DNS-записи должны быть настроены таким образом, чтобы разные подпути (или поддомены) вели к разным сервисам (дашборд, логи, приложение, ArgoCD).
- Возможные провайдеры бесплатных доменов:
  - **DNSHE** — предлагает субдомены `.de5.net`, `.us.ci`, `.cc.cd`, `.bot.cd` с панелью управления и API.
  - **Kevin Service Registry** — предоставляет субдомены (например, `ae.kg`, `cs.do`).

### Тесты
1. Проверить доступность домена через `ping` или `nslookup`.
2. Проверить, что DNS-записи резолвятся корректно (A-запись указывает на нужный IP).
3. Проверить, что по домену открывается страница (даже если это заглушка).

### Критерии приемки
- [ ] Домен зарегистрирован и активен.
- [ ] Настроены DNS-записи для указания на публичный IP-адрес или балансировщик Cloud.ru.
- [ ] Домен доступен из публичной сети.
- [ ] Срок действия домена позволяет использовать его в течение всего проекта (с возможностью продления).

## Спецификация 2: Подключение домена к проекту в Cloud.ru

### Намерение
Связать зарегистрированный общедоступный домен с инфраструктурой Cloud.ru, чтобы трафик с домена направлялся в кластер Kubernetes и сервисы, развернутые в нем.

### Требования
1. Домен должен быть привязан к проекту (пространству имен или кластеру) в Cloud.ru.
2. Настроить Ingress-контроллер или балансировщик нагрузки в Cloud.ru для приема трафика с домена.
3. Обеспечить маршрутизацию трафика с разных путей (`/`, `/logs`, `/app`, `/argo`) на соответствующие сервисы внутри кластера.

### Ограничения
1. Используется управляемый кластер Kubernetes в Cloud.ru (Managed Kubernetes).
2. Для публикации сервисов используется Ingress с TLS-сертификатами (Let's Encrypt или собственные).
3. Настройка должна быть воспроизводима через Infrastructure as Code (Terraform, Helm или YAML-манифесты).

### Контекст
- Cloud.ru предоставляет сервис Managed Kubernetes, который позволяет создавать кластеры и управлять ими через консоль или API.
- Для подключения домена потребуется:
  - Внешний IP-адрес (LoadBalancer) или Ingress-контроллер (например, NGINX Ingress).
  - Настройка DNS-записей у провайдера домена на этот IP.
  - Создание Ingress-ресурсов в Kubernetes для маршрутизации по путям.

### Тесты
1. Проверить, что запрос к `https://<домен>/` возвращает дашборд.
2. Проверить, что запрос к `https://<домен>/logs` возвращает систему логирования.
3. Проверить, что запрос к `https://<домен>/app` возвращает приложение.
4. Проверить, что запрос к `https://<домен>/argo` возвращает ArgoCD UI.

### Критерии приемки
- [ ] Домен привязан к проекту в Cloud.ru.
- [ ] Настроен Ingress с правилами маршрутизации для всех четырех сервисов.
- [ ] TLS-сертификаты установлены и работают (HTTPS).
- [ ] Все сервисы доступны по соответствующим путям домена.

## Спецификация 3: Доступ через домен к дашборду, системе логирования, приложению и ArgoCD

### Намерение
Обеспечить пользователям возможность перехода по единому домену к четырем различным компонентам системы: дашборд (обзор состояния), система логирования (сбор и просмотр логов), приложение (целевое веб-приложение) и ArgoCD (интерфейс GitOps).

### Требования
1. По пути `/` должен открываться дашборд (например, Kubernetes Dashboard или Grafana).
2. По пути `/logs` должна открываться система логирования (например, Loki + Grafana или ELK).
3. По пути `/app` должно открываться развернутое приложение с веб-интерфейсом.
4. По пути `/argo` должен открываться интерфейс ArgoCD.

### Ограничения
1. Все сервисы должны быть доступны по HTTPS.
2. Используется единый домен и единый Ingress-контроллер.
3. Аутентификация на сервисах может быть настроена отдельно (базовая аутентификация, SSO или интеграция с ArgoCD SSO).

### Контекст
- ArgoCD может быть настроен с использованием Ingress и пользовательского домена.
- Для системы логирования и дашборда также создаются отдельные Ingress-правила.

### Тесты
1. В браузере перейти по `https://<домен>/` и убедиться, что открывается дашборд.
2. Перейти по `https://<домен>/logs` и убедиться, что открывается система логирования.
3. Перейти по `https://<домен>/app` и убедиться, что открывается приложение.
4. Перейти по `https://<домен>/argo` и убедиться, что открывается ArgoCD UI.

### Критерии приемки
- [ ] По каждому из четырех путей открывается соответствующий сервис.
- [ ] Все сервисы используют HTTPS.
- [ ] Интерфейсы сервисов работают корректно (не возникает ошибок 404 или 500).

## Спецификация 4: Развертывание приложения с веб-интерфейсом по HTTPS (2–4 инстанса, СУБД, Kafka)

### Намерение
Развернуть целевое веб-приложение в кластере Kubernetes с обеспечением отказоустойчивости (2–4 реплики), использованием СУБД для хранения данных и Kafka для обработки событий/сообщений.

### Требования
1. Приложение должно иметь веб-интерфейс, доступный по HTTPS.
2. Приложение должно быть развернуто в количестве от 2 до 4 инстансов (реплик) для обеспечения отказоустойчивости.
3. Должна быть развернута СУБД (PostgreSQL или MySQL) для хранения данных приложения.
4. Должен быть развернут брокер сообщений Kafka для асинхронного обмена данными.
5. Все компоненты должны быть развернуты в кластере Kubernetes (или использовать управляемые сервисы Cloud.ru).

### Ограничения
1. Используются только ресурсы, предоставляемые Cloud.ru (Managed Kubernetes, управляемые СУБД и т.д.).
2. Приложение должно быть контейнеризировано (Docker-образ) и храниться в реестре (например, Artifact Registry Cloud.ru).
3. СУБД и Kafka должны быть настроены с учетом сохранности данных (Persistent Volumes).

### Контекст
- Cloud.ru предоставляет управляемые СУБД PostgreSQL, что может быть использовано для упрощения администрирования.
- Kafka может быть развернута как StatefulSet в Kubernetes или использован управляемый сервис, если доступен.
- Приложение должно быть сконфигурировано через ConfigMap и Secrets для подключения к СУБД и Kafka.

### Тесты
1. Проверить, что приложение доступно по HTTPS через домен (по пути `/app`).
2. Проверить, что работает 2–4 реплики приложения (`kubectl get pods`).
3. Проверить подключение приложения к СУБД (выполнить запрос к базе).
4. Проверить, что приложение может отправлять и получать сообщения через Kafka.

### Критерии приемки
- [ ] Приложение развернуто с 2–4 репликами.
- [ ] Приложение доступно по HTTPS.
- [ ] СУБД развернута и доступна для приложения.
- [ ] Kafka развернута и доступна для приложения.
- [ ] Все компоненты работают стабильно.

## Спецификация 5: Развертывание кластера Kubernetes (1 мастер + 2 инфра-ноды + 3 ноды под приложения)

### Намерение
Создать кластер Kubernetes с четким разделением ролей узлов: мастер-нода для управления кластером, инфра-ноды для размещения инфраструктурных сервисов (Ingress, мониторинг, логирование, ArgoCD), воркер-ноды для размещения пользовательских приложений.

### Требования
1. Кластер должен состоять из:
   - **1 мастер-нода** — только для управления кластером (не должно быть пользовательских и инфра-подов).
   - **2 инфра-ноды** — для размещения инфраструктурных продуктов (Ingress-контроллер, система мониторинга, логирования, ArgoCD и т.д.).
   - **3 воркер-ноды** — для размещения пользовательских приложений.
2. Все узлы должны быть частью одного кластера Kubernetes.
3. На мастер-ноде не должно быть пользовательских и инфра-подов (taints и tolerations должны быть настроены соответствующим образом).

### Ограничения
1. Используется Managed Kubernetes от Cloud.ru.
2. Конфигурация узлов (количество vCPU, RAM) должна быть достаточной для планируемой нагрузки.
3. Настройка taints/tolerations должна быть выполнена на этапе создания кластера или после.

### Контекст
- В Cloud.ru можно создать кластер с несколькими группами узлов (node groups) с разными характеристиками.
- Для разделения нагрузок используются `nodeSelector` и `taints/tolerations`.
- Инфра-ноды должны иметь taint, чтобы обычные приложения на них не планировались, а инфра-сервисы — имели toleration.

### Тесты
1. Проверить количество узлов в кластере (`kubectl get nodes`).
2. Проверить, что на мастер-ноде нет подов, кроме системных (`kubectl get pods -A -o wide | grep <master-node>`).
3. Проверить, что инфра-поды (Ingress, ArgoCD, мониторинг) запущены на инфра-нодах.
4. Проверить, что пользовательские приложения запущены на воркер-нодах.

### Критерии приемки
- [ ] Кластер развернут с 6 узлами (1 мастер + 2 инфра + 3 воркер).
- [ ] Мастер-нода не содержит пользовательских и инфра-подов.
- [ ] Инфра-продукты развернуты на инфра-нодах.
- [ ] Приложения развернуты на воркер-нодах.

## Спецификация 6: CI/CD пайплайн в GitHub (развертывание кластера, инфраструктуры, приложения)

### Намерение
Реализовать CI/CD пайплайн в GitHub, который автоматизирует развертывание всех компонентов системы: кластера Kubernetes, инфраструктурных сервисов и самого приложения.

### Требования
1. Пайплайн должен состоять из трех сценариев (workflows или stages):
   - **6а:** Развертывание кластера Kubernetes в Cloud.ru.
   - **6б:** Развертывание инфраструктурных проектов (Ingress, мониторинг, логирование, ArgoCD) на инфра-нодах.
   - **6в:** Развертывание приложения на воркер-нодах.
2. Все сценарии должны быть реализованы с использованием GitHub Actions.
3. Инфраструктурные проекты должны разворачиваться на инфра-нодах.
4. Приложения должны разворачиваться на воркер-нодах.

### Ограничения
1. Используются бесплатные ресурсы GitHub Actions (или с ограничениями).
2. Для доступа к Cloud.ru используются секреты GitHub (API-ключи, kubeconfig и т.д.).
3. Конфигурация кластера и приложений должна храниться в Git-репозитории (Infrastructure as Code).

### Контекст
- Для развертывания кластера можно использовать Terraform или Cloud.ru CLI/API.
- Для развертывания приложений в Kubernetes используются `kubectl` или Helm.
- Пайплайн должен быть идемпотентным и безопасным.

### Тесты
1. Запустить пайплайн вручную и проверить, что кластер создается.
2. Проверить, что инфраструктурные сервисы разворачиваются на инфра-нодах.
3. Проверить, что приложение разворачивается на воркер-нодах.

### Критерии приемки
- [ ] Пайплайн содержит три отдельных сценария (или stages).
- [ ] Сценарий 6а успешно создает кластер Kubernetes.
- [ ] Сценарий 6б успешно развертывает инфраструктурные сервисы на инфра-нодах.
- [ ] Сценарий 6в успешно развертывает приложение на воркер-нодах.
- [ ] Все сценарии могут быть запущены автоматически или вручную.

## Спецификация 7: Принцип работы пайплайна (merge в ветку release)

### Намерение
Автоматизировать развертывание приложения в кластер Kubernetes при каждом объединении изменений в ветку `release`, чтобы обеспечить непрерывную доставку.

### Требования
1. Пайплайн должен запускаться автоматически при создании merge-коммита в ветку `release` (или при пуше в эту ветку).
2. При запуске пайплайна должно происходить развертывание приложения в кластер Kubernetes.
3. Развертывание должно быть безопасным (можно использовать стратегии Rolling Update или Blue-Green).

### Ограничения
1. Пайплайн запускается только для ветки `release` (не для других веток).
2. В процессе развертывания не должны затрагиваться инфраструктурные компоненты (они развертываются отдельно).
3. Используется GitOps-подход: манифесты приложения хранятся в репозитории и применяются в кластер.

### Контекст
- GitHub Actions поддерживают триггеры на push в определенные ветки.
- Для развертывания приложения можно использовать `kubectl apply` или Helm upgrade.
- Желательно использовать ArgoCD для синхронизации состояния кластера с репозиторием (см. спецификацию 8).

### Тесты
1. Создать merge-коммит в ветку `release` (или выполнить push).
2. Проверить, что пайплайн запустился автоматически.
3. Проверить, что приложение обновилось в кластере.

### Критерии приемки
- [ ] Пайплайн автоматически запускается при merge в `release`.
- [ ] Приложение развертывается в кластере.
- [ ] Другие компоненты (инфраструктура) не затрагиваются.
- [ ] В случае ошибки развертывания пайплайн завершается с ошибкой (fail fast).

## Спецификация 8: Реализация методологии GitOps

### Намерение
Внедрить GitOps как основной подход к управлению инфраструктурой и приложениями, где Git-репозиторий является единственным источником истины (single source of truth), а все изменения применяются автоматически через оператора в кластере.

### Требования
1. Все манифесты Kubernetes (для инфраструктуры и приложений) должны храниться в Git-репозитории.
2. В кластере должен быть развернут GitOps-оператор (ArgoCD или Flux), который отслеживает изменения в репозитории и автоматически применяет их в кластере.
3. Изменения в репозитории (например, обновление образа приложения) должны автоматически синхронизироваться с кластером.
4. Должна быть реализована модель pull-based (оператор сам забирает изменения из Git).

### Ограничения
1. Используется ArgoCD (предпочтительно, так как он упоминается в требованиях).
2. Репозиторий должен быть доступен для ArgoCD (публичный или с настроенным доступом).
3. Секреты должны храниться безопасно (например, с использованием Sealed Secrets или HashiCorp Vault).

### Контекст
- ArgoCD может быть установлен в кластер и настроен на отслеживание репозитория.
- В CI/CD пайплайне (спецификация 6) достаточно обновить манифесты в репозитории (например, изменить тег образа), а ArgoCD автоматически применит изменения.
- ArgoCD поддерживает управление несколькими приложениями (App-of-Apps pattern).

### Тесты
1. Изменить манифест приложения в репозитории (например, увеличить количество реплик).
2. Проверить, что ArgoCD автоматически синхронизировал изменения и применил их в кластере (в течение заданного интервала).
3. Проверить, что состояние кластера соответствует состоянию в репозитории.

### Критерии приемки
- [ ] ArgoCD (или Flux) установлен и настроен в кластере.
- [ ] Репозиторий подключен к ArgoCD как источник.
- [ ] Изменения в репозитории автоматически применяются в кластере.
- [ ] В случае расхождения (drift) ArgoCD уведомляет или автоматически исправляет.
- [ ] GitOps-процесс работает для всех компонентов (инфраструктура и приложения).

1. **Приоритеты**: Начать с регистрации домена и создания кластера Kubernetes, затем развернуть инфраструктурные сервисы, после — приложение и GitOps.
